# Native keyboard remapping: implementation decision

Research date: 2026-10-23. Scope: Ultimate Keyboards owns the remapping engine and background service; users do not install Karabiner-Elements. No driver installation, activation, seizure, input injection, or security changes were performed during this research.

## Recommendation

Bundle the **unmodified standalone Karabiner-DriverKit-VirtualHIDDevice code**, including its signed Manager and Daemon, and connect our root remapping service to its C++ client library. Preserve the original signed flat package as a byte-identical provenance resource; the executable driver component inside our product archive must use the canonical expanded component structure described below. Upstream explicitly supports third-party clients: the signed Daemon mediates third-party root clients that do not have pqrs's signing identity. The driver supplies virtual output only; our service must capture physical input and implement all five existing `Rule` variants. Existing `mouse_engine.rs` remains a separate scroll-only CGEventTap; it is not the full keyboard capture mechanism. [Upstream architecture and usage](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/README.md)

An independently branded dext is technically possible but adds Apple-approved DriverKit/HID entitlements, matching provisioning profiles, distribution signing, and maintenance without addressing an unmet output requirement. Directly opening the pqrs dext from our own binary also introduces entitlement/signing requirements; use its signed socket broker. Apple validates extension signatures, locations, and entitlement grants during activation. [Apple entitlement process](https://developer.apple.com/documentation/driverkit/requesting-entitlements-for-driverkit-development), [extension activation](https://developer.apple.com/documentation/systemextensions/installing-system-extensions-and-drivers), [user-client entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.driverkit.userclient-access)

## Input capture and permissions

Use `IOHIDManager` matching keyboard collections, then per-device `IOHIDDeviceOpen(device, kIOHIDOptionsTypeSeizeDevice)` and HID input-value callbacks/queues. Capture only explicitly selected physical keyboards; exclude virtual output and leave pointing/trackpad collections alone. Retain device identity and timestamp through the engine, distinguish repeats from physical transitions, and handle hotplug/removal. Device seizure requires root; **Input Monitoring remains separately required**. The Apple SDK's `hidsystem/IOHIDLib.h` states that `IOHIDCheckAccess(kIOHIDRequestTypeListenEvent)` checks permission and `IOHIDRequestAccess` requests it; open calls can request on the process's behalf. Granting Accessibility to the Tauri app does not prove the root HID service has Input Monitoring.

The full Karabiner implementation uses the same service executable in agent and daemon roles to obtain the relevant user approval. Our packaging must establish and test the actual responsible binary's TCC identity; copying an entitlement or using sudo does not solve this. [Pinned upstream permissions and capture notes](https://github.com/pqrs-org/Karabiner-Elements/blob/1eff53ce872bbb8f8ad9fb8c1d778b4903db0677/DEVELOPMENT.md#permissions)

Fail open: do not seize until output readiness and engine configuration are confirmed. On output loss, permission loss, engine failure, disable, sleep/session transition, or configuration replacement, release output state and close captured devices promptly. Ensure releasing one physical key does not release a modifier still held by another source. Do not assume seizure gives exclusive ownership against another remapper: upstream documents multiple-client edge cases, especially after wake. Detect existing remappers and leave activation pending instead of racing them.

**macOS 26.4 distinction:** issue #4402 documents a beta-1 built-in SPI keyboard restriction (`IOServiceOpen` denied, protected-device entitlement in logs). The same primary issue records restored normal operation in **26.4 beta 3**. This is not evidence of a permanent 26.4+ prohibition. Current target is macOS **26.5.2 (25F84)**, as reported by the lead. Test its real built-in keyboard instead of disabling security or requesting a private entitlement. [Regression evidence](https://github.com/pqrs-org/Karabiner-Elements/issues/4402#issuecomment-3916863747), [beta-3 restoration](https://github.com/pqrs-org/Karabiner-Elements/issues/4402#issuecomment-3993085715)

A CGEventTap fallback is a separately disclosed reduced-capability mode: Secure Event Input prevents capture and per-device attribution is unavailable. Virtual-HID output reenters the tap without reliable original source tags; upstream tracks matching emitted events to suppress loops. It is not an automatic substitute for failed full-HID acceptance. [Current upstream fallback notes](https://github.com/pqrs-org/Karabiner-Elements/blob/1eff53ce872bbb8f8ad9fb8c1d778b4903db0677/DEVELOPMENT.md#cgeventtap-fallback-behavior)

## Service, authentication, and package lifecycle

Place our LaunchDaemon plist in the calling app's `Contents/Library/LaunchDaemons`; register with `SMAppService.daemon(plistName:)`. Daemons run only after an admin enables them and can start on subsequent boots. Report `.notRegistered`, `.requiresApproval`, `.enabled`, `.notFound`, launch errors, and runtime health separately. An enabled service is not proof of a connected driver. Use `unregister()` for removal; never reset the machine-wide background-task database. Upstream supplies `examples/SMAppServiceExample` and an Interactive-process daemon plist. [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [daemon placement](https://developer.apple.com/documentation/servicemanagement/smappservice/daemon(plistname:)), [registration semantics](https://developer.apple.com/documentation/servicemanagement/smappservice/register())

Use authenticated XPC between unprivileged UI and our root daemon. Before `resume()`, set an exact signing requirement on **both peers**, covering Apple signing anchor, intended Team ID, and exact bundle identifier. Apple provides `NSXPCConnection.setCodeSigningRequirement`. Never authorize from PID, executable name, or caller-supplied path. Restrict methods to bounded configuration/status/enable/disable operations; validate rules again in the daemon, associate configuration with the appropriate active user, and expose no arbitrary root execution, filesystem write, or input injection endpoint. A local-only signing requirement must stay explicit and separate from the distribution requirement. [Apple peer authentication API](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:))

Ship the original signed upstream flat package intact as a separate provenance resource. For the executable driver component, retain the canonical `productbuild` archive structure: an expanded component containing `PackageInfo`, `Payload`, `Bom`, and `Scripts`, each compared byte-for-byte with the original package’s corresponding archive member. Preserve and verify the upstream payload’s code signatures; this does not preserve the flat package’s installer signature on the executable component, so our final product archive needs its own distribution signature. Do not replace expanded executable components with opaque nested flat `.pkg` files. Invoke the upstream Manager for activation and surface macOS approval/restart outcomes. Keep the signed Manager's own dext layout. The package installs `/Applications/.Karabiner-VirtualHIDDevice-Manager.app` and its support-directory Daemon; it does not install Karabiner-Elements. **Coexistence matters:** upstream preinstall deletes/replaces its shared directories and postinstall kills its Daemon. Reuse a compatible installed component; do not silently upgrade, downgrade, uninstall, or stop another product's shared driver. Default Ultimate Keyboards uninstall removes only our registration/configuration. [Packaging script](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/make-package.sh), [postinstall](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/pkginfo/Scripts/postinstall)

Redistribution is permitted by the repository's Unlicense, explicitly including binaries. Client/report headers instead carry Boost Software License 1.0 notices, and vendored dependencies carry their own notices: retain those and ship a dependency notice inventory. Do not imply upstream endorsement. [Repository license](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/LICENSE.md), [client license notice](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/include/pqrs/karabiner/driverkit/virtual_hid_device_service/client.hpp)

## Proof and remaining acceptance

Locally verified without activation: source pin and package hash; `pkgutil --check-signature` reports Developer ID Installer **G43BCU2T37** and trusted Apple notarization; `xcrun clang++ -std=c++23 -fsyntax-only` successfully includes the pinned client and vendor headers with Xcode 26.4. Rebuilding the complete upstream v8.6.0 project documents Xcode 27+, but consuming its client and signed package does not require rebuilding its dext. Existing package 8.5.0 shares protocol 7. None of these checks proves active input/output.

The lead's identity audit found local development identities but no Developer ID Application identity. Public distribution of our app/helper and final installer requires the corresponding distribution signing/notarization credentials; the signed pqrs package does not sign our code. Full native activation also requires user-visible admin/background/driver/TCC approvals. These are external acceptance gates, not reasons to stop offline implementation.

Acceptance criteria:

1. Pure engine tests cover simple remaps, ordered rules, simultaneous combos (including unsuccessful chord replay), layers, 150 ms homerow tap/hold behavior, modifier ownership, repeats, configuration swaps, device removal, and all-key release.
2. C ABI build/link and report-layout checks pass; mismatch/error states disable capture. XPC tests reject unsigned/wrong-team/wrong-identifier peers and malformed/oversized rules.
3. Built `.app` contains helpers/plists/resources; signature and package inventory checks pass. Verify the byte-identical upstream provenance archive, exact executable driver component members, and unchanged vendor code signatures. PackageKit must parse every selected `outer.pkg#component.pkg` URL with the expected identifier/version and initialize the in-memory install request. Then separately verify the privileged install. Clean-machine install needs no Karabiner-Elements app. Existing compatible pqrs installation is preserved.
4. With approvals granted, verify actual USB/Bluetooth and built-in keyboard capture → engine → virtual output, including Caps Lock, Fn, modifiers, hold/chord timing, secure input, and no doubled events. Keep an independent recovery keyboard available for this test.
5. Verify service quit/crash, output daemon loss, sleep/wake, login/logout, hotplug, permission revocation, disabled mode, and uninstall restore ordinary input without stuck keys or changed trackpad behavior.
6. Report implementation, automated checks, signed package checks, and live hardware proof separately. Until item 4/5 executes, full native remapping remains unverified even when compilation succeeds.

## 2026-10-24 installer admission failure and archive correction

The actual user-initiated Installer attempt failed before installing the selected product. The local primary receipt, [`/var/log/install.log`](/var/log/install.log:245063), records at **2026-10-24 01:26:50 -04** `PKInstallRequestErrorDomain Code=2`, naming `UltimateKeyboards-0.3.0.pkg#UltimateKeyboards-Application.pkg`; line 245084 then reports that package URL “not supported by PK.” Earlier `installer -showChoicesXML` and package metadata checks had succeeded. Those checks therefore did not establish admission by the parser used for installation.

The rejected builder replaced the expanded component directories produced by `productbuild` with opaque signed flat `.pkg` files, then flattened the outer archive. The corrected format keeps canonical expanded executable components. The original pqrs flat package remains separately available as a byte-identical provenance resource, while its executable component preserves the exact `PackageInfo`/`Payload`/`Bom`/`Scripts` member bytes and vendor payload signatures. Preserving the upstream installer archive must not make the executable product structure invalid.

An independent, unprivileged check against this Mac’s system `PackageKit.framework` reproduced the failure: `PKPackage +packageWithURL:` returned `nil` for the old product’s Application and Helper fragment URLs, even though `+canInitWithURL:` returned `YES`. The latter is insufficient. The reusable [read-only PackageKit admission helper](../../native/packaging/packagekit-preflight.m) parses each component, reports its identifier/version, constructs `PKPackageSpecifier`, and initializes `PKInstallRequest` in memory. It does not authorize, create or submit an install session, run sizing/staging preflight, or begin installation. These private selectors are runtime-checked local diagnostics, not a supported application API contract.

For every rebuilt product, require nonnil component parsing, exact identifier/version matches, and successful in-memory request initialization; retain the negative old-archive regression. Record this separately from archive member/signature comparisons. A successful admission check proves that the previous structural rejection is resolved; it does **not** prove successful privileged installation, service registration, driver approval, Input Monitoring, physical capture, or live remapping. The corrected artifact’s admission receipt and the subsequent privileged install/live acceptance must be reported independently; metadata-only checks cannot substitute for either.

## 2026-10-24 passive descriptor investigation: built-in keyboard report 63

The first passive service inventory matched four keyboard services but admitted none. The built-in `Apple Internal Keyboard / Trackpad` (`Built-In=true`, FIFO transport, primary usage `0001/0006`) contains normal key elements, generated array index elements, and one opaque input element. The sanitized fixture is `native/service/tests/fixtures/macos-26.5.2-passive-devices.json`. Its vendor element is cookie 297, `Input_Misc`, page/usage `ff00/0006`, report ID 63, non-array, non-relative, logical range 0–255, reported size 512 bits/count 64, under collection cookie 3 with the same vendor usage. These are descriptor facts, not captured input values.

**Array indices are resolved.** The installed Apple SDK's `IOKit/hid/IOHIDElement.h`, documentation for `IOHIDElementIsArray` at lines 228–240, explicitly distinguishes generated array indices (`isArray=true`, usage `0xffffffff`) from the variable elements representing possible array usages. Apple's published `IOHIDElementPrivate::arrayHandlerElement` constructs that sentinel and tracks selectors to update individual child states. A narrowly checked array-backing classification is supported; it must not exclude the generated per-key elements. [Apple array handler and selector handling](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDFamily/IOHIDElementPrivate.cpp#L650)

**The vendor collection has a name, but the payload remains opaque.** Apple's historical `IOHIDFamily-1035.41.2` header defines `ff00/0006` as `kHIDUsage_AppleVendor_Keyboard`, an application collection. This differs from Apple vendor *key* page `ff01` and Top Case page `00ff`. Current published `IOHIDFamily-2238.100.59` commit `777ccd9698845aadf711e32d843c8c9b777431d9` has a license-only `AppleHIDUsageTables.h`; the current public SDK does not supply that vendor header. No reviewed Apple source defines the content of this hardware's report 63. Naming the collection does not identify its binary payload as diagnostics, metadata, keys, or a safe byte stream to replay. [Historical Apple definition](https://github.com/apple-oss-distributions/IOHIDFamily/blob/IOHIDFamily-1035.41.2/IOHIDFamily/AppleHIDUsageTables.h#L62)

**The synthetic raw-report mirror hypothesis is contradicted by published construction.** `IOHIDElementContainer::createReportHandlerElements` calls `reportHandlerElement`, whose constructor sets relative=true, count=1, leaves initialized usage page/usage at zero, and registers without a parent collection. `IOHIDDeviceClass` retrieves these separately into `_reportElements` with a null parent. Cookie 297 has different flags, usage, count, and a real parent. Size 512/count 64 alone is insufficient: `valueElement` also aggregates repeated non-array fields into one large element while retaining the original count. Do not exempt this element as a generated mirror. [Container construction](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDFamily/IOHIDElementContainer.cpp#L500), [mirror constructor](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDFamily/IOHIDElementPrivate.cpp#L388), [value aggregation](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDFamily/IOHIDElementPrivate.cpp#L255), [separate report elements](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDLib/IOHIDDeviceClass.m#L289)

### Scoped decision and remaining verification

The actual driver's advertised keyboard pairs plus the exact upstream conversion filter support a **narrow non-key-channel classification for ordinary keyboard-event remapping on this descriptor**, without claiming to decode or preserve arbitrary vendor traffic. Any implementation exception must check the exact non-array, non-relative `Input_Misc` vendor element, report ID/shape/logical range and parent collection, and confirm it is absent from the actual driver's supported keyboard pairs. Unknown digital controls, other vendor pages/usages, changed report shapes, missing routing evidence, relative axes, and pointer/digitizer collections remain blocked. This is a candidate justified classification, not authorization to capture or a live-pass result.

Before accepting it, preserve the static report-descriptor item receipt for ID 63 and test changed-metadata rejection against the sanitized fixture. A supported-pairs list describes keyboard-event routing; it does not prove every private driver behavior is preserved. Live acceptance must specifically establish ordinary keys, Fn/media, pointer/trackpad behavior, disable/recovery and no duplication. If the product instead requires preservation of report 63's arbitrary payload or every private firmware feature, that stronger requirement remains unresolved and needs an Apple-provided report/transport contract or documented collection isolation. No raw keyboard reports or typed keys were read in this investigation.

Static descriptor follow-up: `native/service/tests/fixtures/macos-26.5.2-static-descriptor.json` records a 189-byte **report descriptor**, not an input report. Its report-63 input item declares **8 bits × 64**, usage `ff00/0006`, parent application collection `ff00/0006`, flags **`0x22`**: Data, Variable, Absolute, No Preferred State. Buffered Bytes (`0x0100`) and Constant (`0x01`) are not set. Therefore neither “constant padding” nor “buffered metadata” is a supported explanation. The aggregate 512-bit IOKit element is consistent with Apple's value-element aggregation. [Apple flag definitions](https://github.com/apple-oss-distributions/IOHIDFamily/blob/777ccd9698845aadf711e32d843c8c9b777431d9/IOHIDFamily/IOHIDDescriptorParserPrivate.h#L40)

Implementation decision: permit only the ordinary keyboard-event scope described above, with both the exact static descriptor/element classification and the actual descendant event driver's supported-pairs evidence; retain rejection of every unrecognized key-shaped input. The report-63 payload is deliberately outside this scope and remains undecoded. This decision resolves the classification blocker for a narrowly guarded implementation; hardware capture, Fn/media parity and recovery acceptance remain separate, unperformed checks in this research receipt.

## Broker client isolation: virtual keyboard ownership

Pinned standalone broker v8.6.0 maintains **a separate virtual keyboard per downstream socket peer**. `virtual_hid_device_service_clients_manager` creates a `client_entry` keyed by `peer_id`; each entry creates its own keyboard `io_service_client`. Reset resolves only that peer's entry. Closing a peer erases only that entry, whose cleanup drops its own keyboard, pointing, and status connections. [Peer ownership and reset](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/Daemon/include/virtual_hid_device_service_clients_manager.hpp#L37), [peer disconnect](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/Daemon/include/virtual_hid_device_service_server.hpp#L173), [entry cleanup](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/Daemon/include/virtual_hid_device_service_clients_manager.hpp#L377)

The isolation continues into the dext: every `IOServiceOpen` obtains a newly created user client; that user client creates and retains its keyboard as `ivars->keyboard`. Its reset dispatch calls that object's `reset()`, and its teardown releases that object. Our init/reset/disconnect therefore does not explicitly clear another client's virtual keyboard state. This is source-level ownership proof, not an executed concurrency test. [IOService connection](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/Daemon/include/io_service_client.hpp#L443), [new user client](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/DriverKit/Karabiner-DriverKit-VirtualHIDDevice/org_pqrs_Karabiner_DriverKit_VirtualHIDDeviceRoot.cpp#L58), [per-user-client keyboard/reset](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice/blob/v8.6.0/src/DriverKit/Karabiner-DriverKit-VirtualHIDDevice/org_pqrs_Karabiner_DriverKit_VirtualHIDDeviceUserClient.cpp#L102)

The broker process and driver installation remain shared: stopping/replacing them affects all clients. Independent output devices also do not establish safe concurrent seizure/remapping of one physical keyboard; that remains a separate conflict and acceptance concern. No driver client connection was made for this ownership check.
