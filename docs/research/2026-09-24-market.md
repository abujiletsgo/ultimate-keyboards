Evidence labels: OBSERVED = read on the cited page today; INFERRED = derived from cited pages; SPECULATIVE = flagged.

## B. Physical layout formats

| Concept | KLE serialized JSON | QMK `info.json` `layouts.LAYOUT.layout[]` | ZMK `zmk,physical-layout` `keys` | keymap-editor `info.json` |
|---|---|---|---|---|
| Container | `[ {meta}, [row...], ... ]`; strings = key labels (legends split by `\n`), objects = property changes for following keys | `{"layouts": {"LAYOUT_x": {"layout": [ {...} ]}}}` | `keys = <&key_physical_attrs w h x y r rx ry>, ...;` inside a node with `compatible = "zmk,physical-layout"`, `display-name`, `transform = <&t>`, `kscan = <&k>` | `{"layouts": {...}}` like QMK but `row`/`col` instead of `matrix` |
| Units | key-units (1u), degrees | key-units, degrees | centi-keyunits (100 = 1u), centidegrees (positive = clockwise); negatives written as `(-3000)` | key-units, degrees |
| Position | `x`,`y` relative offsets from cursor; `rx`/`ry` reset the cursor; `w`,`h` reset to 1 after each key (stateful) | `x`,`y` absolute from keyboard top-left, per-key top-left (stateless: "inheriting no properties from the keys that came before") | `x`,`y` absolute uint, top-left | absolute |
| Rotation | `r` persists across keys; `rx`,`ry` absolute pivot | `r`,`rx`,`ry` present; docs say "Currently not implemented" (Configurator and keymap-drawer still honor them) | `r`,`rx`,`ry` ints; `rx`/`ry` absolute in centi-keyunits | `r`,`rx`,`ry` |
| Matrix link | none (VIA uses `"row,col"` legends) | `matrix: [row, col]` required | key index = keymap position; `transform` phandle to `zmk,matrix-transform` (`rows`, `columns`, `row-offset`, `col-offset`, `map = <RC(r,c) ...>`) | `row`,`col` are rendering order only, "not correlated to GPIO pins" |
| Extras | `x2,y2,w2,h2` second rect (ISO enter, stepped); `c,t,f,a,p,g,l,n,d` styling | `label`, `encoder`, `hand` ("L"/"R"/"*"), `layout_aliases`, `community_layouts` | position map `zmk,physical-layout-position-map` (`positions`, `complete`); needs `#include <physical_layouts.dtsi>`; Studio needs `keys` and no chosen `zmk,matrix-transform`; `CONFIG_ZMK_PHYSICAL_LAYOUT_KEY_ROTATION` default on | first layout is default; multiple layouts keyed to matrix-transform labels |
| Source | https://github.com/ijprest/keyboard-layout-editor/wiki/Serialized-Data-Format | https://docs.qmk.fm/reference_info_json | https://zmk.dev/docs/development/hardware-integration/physical-layouts ; https://zmk.dev/docs/config/layout | https://github.com/nickcoutsos/keymap-editor/wiki/Defining-keyboard-layouts |

Field mapping to a canonical internal key `{x, y, w, h, r, rx, ry, matrix?}` in key-units/degrees:

- KLE: run the stateful cursor (apply `x`/`y` deltas, emit key at cursor with current `w`/`h`/`r`/`rx`/`ry`, advance cursor by `w`, reset `w`/`h` to 1; a new row resets x to 0 and y += 1; setting `rx`/`ry` moves the cursor to the pivot).
- QMK info.json: copy fields as-is.
- ZMK: divide all seven ints by 100 (`r` from centidegrees to degrees); export multiplies by 100, rounds to int, wraps negatives in parentheses.
- keymap-editor: copy; map `row`/`col` to `matrix` only if the user confirms they are real matrix coordinates.
- keymap-drawer (MIT) already implements all four importers and is the reference implementation to crib from: https://github.com/caksoylar/keymap-drawer

## C. ZMK pointing devices

Core primitives (OBSERVED):

- Kconfig: `CONFIG_ZMK_POINTING=y`; `CONFIG_INPUT=y`; bus (`CONFIG_SPI=y` or I2C); optional `CONFIG_ZMK_POINTING_SMOOTH_SCROLLING=y`; `CONFIG_INPUT_THREAD_STACK_SIZE` (512 default, 1024 on split peripherals). Split: enable pointing on both central and peripheral shields when the device is on the peripheral.
- Listener: `zmk,input-listener { device = <&sensor>; input-processors = <...>; child { layers = <N>; input-processors = <...>; process-next; }; }`.
- Split: shared `.dtsi` gets `split_inputs { glidepoint_split: glidepoint_split@0 { compatible = "zmk,input-split"; reg = <0>; }; }`; peripheral overlay sets `device`, central enables the listener.
- Processors (`#include <input/processors.dtsi>`): `zip_xy_scaler mul div`, `zip_x_scaler`, `zip_y_scaler`, `zip_scroll_scaler`, `zip_xy_transform (INPUT_TRANSFORM_XY_SWAP | INPUT_TRANSFORM_X_INVERT | INPUT_TRANSFORM_Y_INVERT)`, `zip_scroll_transform`, `zip_xy_to_scroll_mapper`, `zip_xy_swap_mapper`, `zip_temp_layer layer timeout_ms` (custom instances take `require-prior-idle-ms`, `excluded-positions`), `zip_button_behaviors`. Custom types: `zmk,input-processor-scaler|transform|code-mapper|behaviors|temp-layer`.
- Mouse emulation keys `&mkp` (LCLK, RCLK, MCLK, MB4, MB5), `&mmv`, `&msc` with `#include <dt-bindings/zmk/pointing.h>`; `time-to-max-speed-ms` (300) and `acceleration-exponent`. Enabling pointing changes the HID report descriptor, so BLE hosts must re-pair.
- Modules: `config/west.yml` with `manifest.remotes[] {name, url-base}`, `manifest.projects[] {name, remote, revision, import?}`, `self.path: config`.

Sources: https://zmk.dev/docs/development/hardware-integration/pointing ; https://zmk.dev/docs/keymaps/input-processors ; https://zmk.dev/docs/keymaps/input-processors/usage ; https://zmk.dev/docs/keymaps/input-processors/temp-layer ; https://zmk.dev/docs/config/pointing ; https://zmk.dev/docs/keymaps/behaviors/mouse-emulation ; https://zmk.dev/docs/features/modules

What a generic "add a trackball/trackpad" wizard must write:

1. `config/west.yml`: add remote + project (`name`, `remote`, `revision`, optional `import`). Pin `revision` to a tag or ZMK-version branch; ZMK recommends pinning (https://zmk.dev/blog/2025/06/20/pinned-zmk).
2. `config/<shield>.conf` (and peripheral `.conf` for split): `CONFIG_ZMK_POINTING=y`, `CONFIG_INPUT=y`, bus enable, driver-specific flags.
3. `config/<shield>.overlay` (or `.dtsi` shared for split): `&pinctrl` pin selects; bus node `status = "okay"` + `cs-gpios`; sensor node; `zmk,input-listener` with base processors and per-layer child overrides. Community pattern from choovick: move `<&zip_xy_scaler 7 6>`, snipe `<&zip_xy_scaler 1 3>`, scroll `<&zip_xy_scaler 1 10>` + `zip_xy_to_scroll_mapper`; optional `zip_temp_layer` for auto mouse layer. Split adds `zmk,input-split` node on both sides.
4. `build.yaml`: add `snippet: studio-rpc-usb-uart` and `cmake-args: -DCONFIG_ZMK_STUDIO=y` only if the user wants Studio.
5. `.keymap`: `&mkp LCLK` etc. on the mouse layer; `#include <dt-bindings/zmk/pointing.h>` and `#include <input/processors.dtsi>`.

Also https://github.com/Cyb3rDudu/zmk-charybdis (dongle + BLE variants, all revisions pinned).

## D. QMK equivalents

- `rules.mk`: `POINTING_DEVICE_ENABLE = yes`; `POINTING_DEVICE_DRIVER = adns5050 | adns9800 | analog_joystick | azoteq_iqs5xx | cirque_pinnacle_i2c | cirque_pinnacle_spi | paw3204 | paw3222 | pimoroni_trackball | pmw3320 | pmw3325 | pmw3360 | pmw3389 | custom` (only one driver at a time).
- `config.h`: `POINTING_DEVICE_ROTATION_90/180/270`, `POINTING_DEVICE_INVERT_X/Y`, `POINTING_DEVICE_TASK_THROTTLE_MS`, `POINTING_DEVICE_HIRES_SCROLL_ENABLE`, `POINTING_DEVICE_AUTO_MOUSE_ENABLE` + `AUTO_MOUSE_DEFAULT_LAYER`, driver pins/CPI (`PMW33XX_CS_PIN`, `PMW33XX_CPI`), split: `SPLIT_POINTING_ENABLE` with `POINTING_DEVICE_LEFT`, `POINTING_DEVICE_RIGHT`, or `POINTING_DEVICE_COMBINED`.
- Drag-scroll, snipe, and per-layer behavior are C (`pointing_device_task_user`, `report_mouse_t` x/y/h/v/buttons), so a GUI can emit `config.h`/`rules.mk` plus a generated `keymap.c` stanza, but cannot express them as data.
- Keymap paths: External Userspace repo (`qmk config user.overlay_dir=...`, `qmk userspace-add -kb <kb> -km <km>`, `qmk.json`, `qmk userspace-compile`, GitHub Actions builds) keeps `keyboards/<kb>/keymaps/<name>/keymap.{c,json}` outside the QMK fork. Conversions `qmk c2json`, `qmk json2c`, `qmk via2json` exist; docs warn C parsing "may not work with your keymap".
- VIA JSON only covers dynamic keymap + macros + layout options + lighting menus; it cannot express pointing, combos, or tap-dance.

## What flagship means here

Ranked by how many of the nine editors (ZMK Studio, keymap-editor, VIA, Vial, QMK Configurator, Keychron Launcher, Oryx/Keymapp, Glove80 editor, KeyPath) have the capability.

| # | Capability | Have it | Notes |
|---|---|---|---|
| 1 | Visual per-key remap on an accurate physical layout with layer tabs | 9/9 | Table stakes. |
| 2 | Macros editor | 8/9 | Only ZMK Studio lacks it (planned). |
| 3 | Hold-tap / dual-function key builder | 7/9 | Configurator and VIA expose only MT/LT keycodes. |
| 4 | One-click build or flash (cloud compile, in-app flash, or runtime push) | 6/9 | Studio, VIA, Vial, Launcher, Oryx/Keymapp, Glove80. |
| 5 | Combos editor with visual key picker | 5/9 | Vial, keymap-editor, Oryx, Glove80, KeyPath (chords). |
| 6 | Layout variants / physical-layout switching (ISO/ANSI, split spacing, position maps) | 5/9 | Studio, VIA, Vial, Configurator, keymap-editor. |
| 7 | Tap-dance editor | 2/9 | Vial, KeyPath. |
| 8 | Live key/layer view, heatmap, or training | 2/9 | Keymapp, KeyPath. |
| 9 | Custom devicetree/C escape hatch preserved round-trip | 2/9 | Glove80 editor, keymap-editor (tree-sitter). The minimal-diff serializer is the differentiator here. |
| 10 | Pointing-device setup and per-layer tuning (scroll/snipe/temp-layer) | 1/9 partial | Only Glove80's Go60 touchpad page. Open gap. |

Open gap: no competitor combines a file-based, minimal-diff editor with custom physical layouts and a pointing-device wizard. Items 9 and 10 are where the product wins; items 1-6 are what it must match before anyone notices.
